### 2026-08-10 - The polling interval was a literal, and a second copy inside one tick was lost

- Source: Product task 15 from `BACKLOG.md`.
- Summary: `ClipboardPolling` (in `ClipboardMonitor.swift`) is the one place the cadence lives, at 0.25 s in place of the 0.8 s literal inside `startMonitoring`, and `logMissedWrites` says so whenever `changeCount` moves by more than one between two reads. Both halves of the entry, in the order it asked for: making the drop visible is what turns the interval into a question evidence can answer.
- **Measured before choosing, and the numbers are in `docs/DEVELOPMENT.md`.** One `changeCount` read costs 0.75 µs over 200,000 reads, so at 4 Hz the read itself is 3 µs of CPU per second, 0.0003% of a core. The interval's real cost is the timer firing, which the process-level measurement caught: over a 302 s idle window with the popover closed, the dev build used 0.09 s of CPU at 0.8 s and 0.18 s at 0.25 s, 0.030% of one core against 0.050%. The two rows agree on ~0.11 ms per tick plus ~50 ms per 300 s of other idle work, which is what makes them worth quoting at `ps`'s 10 ms resolution.
- **A shorter fixed tick, not an adaptive one.** The entry left both open. An interval that runs fast while the user is active would avoid a cost that is already 0.3 ms of CPU per second, and it would make the recorded source app depend on how recently the user typed, which is a second heuristic sitting behind the first. `Timer.tolerance` is unset for the same reason: coalescing wakeups would widen the worst case past the interval the app advertises, and there is nothing worth buying back.
- **0.25 s rather than 0.1 s, and the reason is wakeups rather than CPU.** The same model puts 0.1 s at ~0.11% of a core, small but 3.6 times the choice, and its extra 6 wakeups a second are exactly the part a CPU-time measurement cannot see. What closes the window is that two deliberate ⌘C presses need a selection change between them, which nobody does inside a quarter second; the losses left below that are programmatic writers, and no interval wins those. It also matches `pendingCaptureRetryDelay`, so "soon" has one meaning in this file.
- **The premise was verified rather than assumed, on a pasteboard of its own.** On a private named `NSPasteboard`, one `clearContents()` plus a write moves the count by exactly 1, two writes move it by 2, and only the later string reads back. Never `NSPasteboard.general`, for the reason the rich-text notes give: fixtures would land on the developer's own clipboard and be captured by the running builds. That measurement also sharpened the log's honesty, since the ordinary staged write (clear, then fill types in later, the case `attemptPendingCapture` exists for) moves the count once and is not reported, while an app clearing twice for one copy is: the count is an upper bound on clips lost, so it drives a log and not a warning to the user.
- **The false positive that would have made the number worthless, which the entry did not anticipate.** At launch `changeCount` is 0 while the pasteboard's is however many writes the machine has seen since boot, so the first read would report thousands of lost clips at every launch. `hasReadChangeCount` gates the log until a real count has been adopted, and `adoptChangeCount` became the single writer of `changeCount` so a capture, a resume and the app's own paste all leave a usable baseline behind rather than only the poll doing so.
- **Debug level, not info.** The message carries no clipboard content and would have been safe in the unified log, but how often a user copies twice in a quarter of a second is behaviour that would then outlive the process, in an app whose claim is that what you copy stays on your Mac. It is a dev-build number on stdout, and `docs/DEVELOPMENT.md` now says how to read one (run from Xcode; nothing collects stdout for the copy `run.sh` installs). The wording says "since the last read" rather than naming a tick, because App Nap can stretch a timer well past its interval.
- **The user-visible sentence moved with the constant.** The Settings copy under "Never save clips from these apps" states the interval as part of admitting the source app is a guess, so it interpolates the constant instead of repeating a number that would drift. That takes `intervalDescription` rather than the `TimeInterval`: a `Text` interpolation builds a `LocalizedStringKey`, which sends a `Double` through `%lf`, so the honest version of the sentence would have shipped reading "every 0.250000 seconds". A test pins the formatting for that reason. `README.md` carries the same sentence and was updated with it.
- What the entry asked to leave alone was left alone: the pause path still adopts the pasteboard's count before the timer restarts (`ClipboardCapturePause.changeCountOnResume`, now through `adoptChangeCount`), and the pending-capture retry is untouched. The retry and the poll now share a cadence and do not interfere: while a capture is pending the count has already been adopted, so the poll finds nothing to do.
- Verification: `xcodebuild test` (TEST SUCCEEDED, 0 failures) with 7 new tests in `MacClipboardTests/SensitiveContentDetectorTests.swift`, beside the pause tests they share a mechanism with: one write missing nothing, two and seven writes counted, a stalled and a rewound count reading as no loss, copies made while paused not reported as lost after a resume, a bound on the interval itself so it cannot quietly be raised, and the formatting of the interval where a user reads it.
- Finished with `./run.sh`, so the dev copy in `~/Applications/MacClipboard-Dev.app` carries the change. The idle measurement above was taken on that build; the only edits after it were comment text and the log's wording.
- Not done: the by-eye and by-log checks. Nobody has watched the ⏱️ line appear for a double write or confirmed the source app is right more often now; the checklist is in `CLAUDE.md` under "When modifying the polling interval". No release build, no version bump.

### 2026-08-10 - A clip did not record which app it came from

- Source: Product task 14 from `BACKLOG.md`.
- Summary: `sourceBundleIdentifier`, an optional String on `PersistedClipboardItem` with an inferred lightweight migration. The row shows the app's icon beside the time, the preview shows its name, and both are resolved from the identifier at display time. `ClipboardSource.swift` (new file) holds the recording rule and `ClipboardSourceAppCatalog`; the capture side is one changed method in `ClipboardMonitor`.
- **The two scoping calls in the entry were kept exactly.** Only the identifier is stored, with name and icon resolved when a row is drawn as `ExcludedAppRow` already does, so a renamed app reads correctly, an uninstalled one reads as its identifier rather than dropping off, and no icon bytes reach a store whose entire storage problem is pictures. And the identifier comes off the *same* `NSWorkspace` read that feeds `ClipboardCapturePolicy`: `captureDecision(for:)` became `captureRead(for:)`, returning the decision and the identifier together, so the guard that may drop a clip and the source recorded on it can never name different apps.
- **The retry path needed the same treatment, which the entry did not mention.** `attemptPendingCapture` exists because some apps write a clip in stages, and it deliberately does not re-check the frontmost app. Re-reading it there for the source would have reintroduced exactly the disagreement the paragraph above prevents, so the first read's value is carried in `pendingSourceBundleIdentifier` and dropped with the rest of the pending state.
- **A re-copy replaces the source, which the entry did not anticipate.** The source is a property of the copy rather than a decision the user made about the clip, so it belongs with `rtfData` and `htmlData` in what `ClipboardHistoryMerger` does not inherit, *and* in the comparison its "already at position 0, nothing to write" short-circuit makes. Without the second half, copying a sentence out of Mail and then out of Slack leaves a row that keeps saying Mail. It cannot make an item claim it came from MacClipboard, because `copyToClipboard` adopts the pasteboard's change count and the app's own writes never come back through capture.
- **Caching turned out to be load-bearing, not an optimisation.** Search matches the source, so a name is resolved for every item in the history on every keystroke; a LaunchServices lookup per item would have made typing over a long history expensive. `ClipboardSourceAppCatalog` caches hits *and* misses behind an `NSLock` (the filter runs on a detached task while rows draw on the main thread), and clears on `NSWorkspace.didLaunchApplicationNotification` so an app installed while MacClipboard is running stops reading as its own bundle identifier without a relaunch.
- **What search matches was narrowed during the work.** The displayed name only, never the bundle identifier of an installed app: "com.google.Chrome" would otherwise make a search for "google", or for "com", return every clip copied out of Chrome. An app that is gone still matches on its identifier, because that is then the only name it has, so the rule stays "search matches what the row shows".
- **Both halves of "filter or search" shipped, and they are different tools.** The entry asked for "a way to filter or search by source app". Search matching came first; the exact filter was added the same day on the requester's ask, on the condition that it stay small. `sourceFilter` is one optional parameter on `ClipboardFilter.filteredItems`, one `@State` on `ContentView`, and a `Menu` that collapses to one icon-width button in the search bar. Typing "Mail" finds the clips that say the word as well as the ones from Mail, which is right for a find; the menu finds only the ones from Mail, which is right for a filter.
- **The menu lists only the apps that have something in the list**, as asked. Read off the current tab and deliberately before the source filter and the search are applied, or picking an app would empty the menu that picked it, and not drawn at all until something has a source, so a history from before this shipped costs nothing. A `Menu` rather than app tabs because the set differs on every Mac and grows with the history. `sourceFilter` is `@State` and dies with the popover: persisting it would be a way to lose clips behind a setting nobody remembers turning on. `revealWrittenItem` clears it, and it is the filter every write there trips, since the four user-made items all have no source.
- Nothing is shown for a clip captured before this change, for a process with no bundle identifier, or for an item the user made themselves. All four builders (`ClipboardTextEdit`, `ClipboardMergedCopy`, `ClipboardTextSplit`, `ClipboardImageTextRecognition`) take no source, so that falls out of their signatures rather than being a rule to remember. An "Unknown app" placeholder was rejected: it claims something about a clip nothing was recorded for, and it would sit on almost every row on the first launch after upgrading.
- Verification: `xcodebuild build` (Debug, BUILD SUCCEEDED) and `xcodebuild test` (TEST SUCCEEDED, 0 failures) with 26 new tests in `MacClipboardTests/ClipboardSourceTests.swift`: 23 covering what is worth recording, the no-frontmost-app case in both the capture guard and the item, every kind of clip carrying a source, the four user-made items carrying none, the three re-copy rules, resolution for an installed and an uninstalled app, the four search rules and the five filter rules, plus 3 store-backed ones for the round trip and for what a row written before the attribute existed loads as.
- The migration was exercised for real, not only inferred: `./run.sh` against the existing 433-row dev store added `ZSOURCEBUNDLEIDENTIFIER` with no load error, old rows read back null, and a copy made afterwards recorded the frontmost app's identifier.
- Finished with `./run.sh`, so the dev copy in `~/Applications/MacClipboard-Dev.app` carries the change.
- Not done: the check by eye. Nobody has looked at the icons in the row, the name in the preview, or the search button in the running popover; the checklist is in `CLAUDE.md` under "When modifying the recorded source app". No release build, no version bump.

### 2026-08-10 - Light and dark followed the system with no way to override

- Source: Product task 13 from `BACKLOG.md`.
- Summary: a System / Light / Dark segmented control in Settings > General, stored as `appearance` and applied by `AppDelegate` as one `NSApp.appearance`. `AppearancePreference` (new file, `Appearance.swift`) holds the three cases, the mapping to AppKit and the fallback. It stays as small as the entry said it should be: nothing here names a colour, and the semantic-colour rule is what makes that possible.
- **The app-wide override was checked before it was trusted, and the check is the one interesting part.** Forcing dark risks the menu bar icon, which is a template image tinted for the appearance it is drawn in: a white glyph on a light menu bar would be the one surface a user cannot choose to stop looking at. Measured with a probe that creates a real status item on a Mac set to light: with `NSApp.appearance` forced to `NSDarkAqua` the status button still reports `NSVibrantLight`, before and after, while a plain window of the same app reports `NSDarkAqua`. AppKit pins the status bar's window to the menu bar's appearance, so the icon is safe by construction rather than by care, and one assignment can cover every other surface including windows built later. That is now written down in `Appearance.swift` and in `docs/DEVELOPMENT.md`, because the next person will ask the same question.
- **`.system` assigns `nil` rather than skipping the assignment.** To `NSApplication`, `nil` means "follow the system", not "leave it alone", so treating System as a no-op would leave the last override in place and picking Dark then System would stay dark with nothing on screen to explain it. There is a test for that direction specifically.
- **The raw string is stored, not an index**, so adding or reordering a case later cannot turn somebody's Dark into Light. Anything unrecognised, from an absent key to a value a later version wrote, reads as System, which is the same fallback an unusable stored hotkey takes and the one state in which both appearances are exercised.
- **Applying it belongs to `AppDelegate`.** Not `UserPreferencesManager`: a preference object is built by tests too, and a side effect in its `didSet` would push the developer's own appearance onto whatever app is hosting them. Not `MenuBarController` either, which is created a quarter of a second into launch and not at all under a test host, while the onboarding window and the installation alerts can be on screen before then. The change is applied on the next main-runloop pass so the assignment is not made inside the SwiftUI update the picker is in.
- Reset puts it back to System, unlike the three preferences Reset leaves alone: nothing is lost and the change is visible as it happens. The Settings caption says which surfaces the choice covers and that the menu bar icon always follows the menu bar.
- Verification: `xcodebuild build` (Debug, BUILD SUCCEEDED) and `xcodebuild test` (TEST SUCCEEDED, 0 failures) with 12 new tests in `MacClipboardTests/AppearancePreferenceTests.swift`, covering the stored strings, every recognised and unrecognised value, the two AppKit appearance names, System clearing an override that Light and Dark set, the order the control is drawn in, and the round trip through `UserPreferencesManager` over a defaults suite of its own including Reset.
- Finished with `./run.sh`, so the dev copy in `~/Applications/MacClipboard-Dev.app` carries the change.
- Not done: the check by eye. The measurement above says the menu bar icon cannot invert, but nobody has watched the popover, Settings, the right-click menu and an alert change appearance in front of them; the checklist is in `CLAUDE.md` under "When modifying the appearance override". No release build, no version bump.

### 2026-08-10 - Text in a copied image could not be read out of it

- Source: Product task 12 from `BACKLOG.md`.
- Summary: `Cmd+R`, and a button in the preview toolbar, read the text in the selected image with Vision on this Mac and save it as a new text item. `ClipboardImageTextRecognition` (new file, `ImageTextRecognition.swift`) holds the value-level half, `ImageTextRecognizing` is the seam in front of Vision, and `ClipboardMonitor.recognizeText` is the one place that touches history. It reuses the editor's model rather than inventing one: the image row is untouched, the text lands through `insertIntoHistory`, masking can only be gained, nothing is trimmed, and the pasteboard is not written.
- **Only when asked, which is the shape of the whole feature.** No preference, no queue, nothing on capture. An accurate pass over a full-screen screenshot is hundreds of milliseconds of CPU, and the storage note says a real history holds 176 images, most pasted once and forgotten.
- **The result is an item, not a field on the image**, as the entry asked. In `associatedText` it would be unsearchable as a clip and could not be edited, starred or deleted on its own, and the image row would stop meaning "what was on the pasteboard".
- **Reading order is rebuilt from the boxes rather than taken from Vision**, which the entry did not anticipate and which turned out to be the substance of the work. Vision's result order is not documented as reading order, and here the order *is* the output. Rendering "Left" and "Right" side by side and running the real request returns two observations at midY 0.262 and 0.253, so without a vertical-overlap rule a two-column image comes out as one column then the other. Same-line boxes are joined with a space; the grouping compares against the row's *first* box, because chaining the comparison lets a column of slightly descending lines collapse into one very tall line; and the lines get a total order by `(midY, minX)` before any grouping, because asking "same line?" inside a `sorted(by:)` predicate is not a transitive ordering.
- **The marker is an attribute, not a note.** The entry allowed either. A note costs nothing to write, but the note field belongs to the user, every other derived-item path here deliberately leaves it alone, and `ClipboardFilter` scores an item with a note above one without, so an auto-note would quietly outrank ordinary matches in every search. `isRecognizedText` is a Boolean on `PersistedClipboardItem` with an inferred lightweight migration, false for every row written before it, shown as `text.viewfinder` in the row and in the preview's metadata line. Not a display-time derivation like the colour swatch, because provenance is not content.
- **The progress and failure states the entry asked for.** The toolbar button becomes a spinner in the same slot, a second ⌘R while one is in flight does nothing, an image with nothing readable gets its own outcome (`noTextFound`) worded so it does not read as a failure, and a failed request says so and adds nothing. The recognition runs on `ClipboardMonitor` rather than in the popover, so closing the popover mid-pass still leaves the new row in history; the view holds only the spinner's state.
- **On-device copy, in the two places it is asked for.** The button's tooltip says the text is read on this Mac before it is pressed, and the status line says it again afterwards. `VNRecognizeTextRequest` needs no entitlement and no network, so the update check remains the app's only unprompted network call.
- A masked image is refused until it is revealed, the same test the editor makes, and text read from a revealed hidden image is hidden. The request is off the main thread throughout, with the `CGImage` taken on the caller's thread because an `NSImage` is not safe to hand to another one.
- Verification: `xcodebuild build` (Debug, BUILD SUCCEEDED) and `xcodebuild test` (TEST SUCCEEDED, 0 failures) with 17 new tests in `MacClipboardTests/ImageTextRecognitionTests.swift`, covering what the action applies to, the ordering and grouping rules including the descending column, whitespace-only boxes, what the item inherits, and the monitor's four outcomes over a store of its own with a stub recogniser. The real Vision path was checked separately against a rendered image, which is where the two-column measurement above comes from.
- Finished with `./run.sh`, so the dev copy in `~/Applications/MacClipboard-Dev.app` carries the change.
- Not done: the interactive pass. Nothing has been read out of a real screenshot in the running popover, and the spinner, the marker and the greyed button have not been checked by eye; the checklist is in `CLAUDE.md` under "When modifying text recognition". No release build, no version bump.

### 2026-08-10 - A hex colour clip showed no colour

- Source: Product task 11 from `BACKLOG.md`.
- Summary: a text clip that is exactly a colour draws a swatch of it in the row, in place of the text icon, and in the preview's metadata row. `ClipboardColorSwatch` is a pure value with the whole parse on it, so every notation and every near miss is stated in tests rather than in the middle of a view. Nothing is stored: there is no attribute, no migration, and a history with no colours in it pays nothing.
- **The scoping rule from the entry is kept exactly, and it is the feature.** Only the whole trimmed clip counts, so `color: #FF5733;` gets nothing and `#FF5733` gets a swatch. Matching anywhere in the text would mark most CSS, most stylesheets and a good deal of ordinary code, and a marker that is on everything says nothing. It is also what makes the parse cheap, since it can refuse on length before allocating.
- Notations: `#RGB`, `#RGBA`, `#RRGGBB`, `#RRGGBBAA`, plus `rgb()` and `rgba()` in both the legacy comma spelling and the CSS Color 4 space-and-slash one. The entry said `rgb()` optionally; it is in because a colour picker's "copy as rgb" is how half of these clips are made, and because the hex printed beside the swatch is then the conversion the user would otherwise do by hand. `rgb` and `rgba` are aliases in that spec, so neither is held to its own component count.
- **The one notation deliberately refused is percentage channels.** `rgb(100%, 0%, 0%)` gets no swatch. It costs a spelling almost nobody copies and keeps every component to one parse rule; alpha still takes a percentage, which is where CSS actually puts them.
- The near misses the entry named are covered and so are the ones it did not. `#1234567` fails on a length no notation has, `#GGHHII` and a ticket reference like `#123abz` fail on content, and `#ＡＢＣ` fails because `Character.isHexDigit` accepts the fullwidth forms and nobody copied those meaning a colour. The exception, decided during the work: out-of-range `rgb(300, 0, 0)` is **clamped, not refused**, because that is what a browser does with it and it is a colour written badly rather than a clip that means something else.
- **"No measurable cost per row" is answered by a cap, not by care.** `maxLength` (40) is checked with `prefix`, so a megabyte of copied CSS costs 41 characters of counting rather than a trim and a lowercase of the whole clip, and the list being a `LazyVStack` means only rows on screen run it. The trade is that a colour padded past the cap gets no swatch, which is a clip nobody has; there is a test pinning both halves.
- **"Legible in light and dark" needed two things, not one.** The border is not decoration: `#FFFFFF` in light mode and `#1E1E1E` in dark are the background with nothing to say where the swatch starts, and they are two of the colours people copy most. It is `Color.secondary`, per the semantic-colour rule. And below full alpha the swatch is drawn over a four-square checkerboard, because a translucent colour over the row background is otherwise indistinguishable from a lighter opaque one, and alpha is the part of `#RRGGBBAA` least readable as text.
- Two smaller calls. The swatch is checked **after** the mask in the row, so a hidden colour clip shows the lock until it is revealed: the colour is content. And the preview prints the hex beside the swatch only when the clip does not already read as that hex in some case (`addsHexLabel`), so the common six-digit item does not get a label repeating the line above it.
- Verification: `xcodebuild build` (Debug, BUILD SUCCEEDED) and `xcodebuild test` (TEST SUCCEEDED, 0 failures) with 22 new tests in `MacClipboardTests/ColorSwatchTests.swift`. They cover the four hex lengths and the nibble expansion, both `rgb()` spellings and the alias rule, alpha as a decimal and as a percentage, clamping, every near miss above, a colour inside other text in five shapes, the length cap on a stylesheet and on a padded colour, trimming, the hex label and when it is printed, translucence, and images and file items never being read as colours.
- Finished with `./run.sh`, so the dev copy in `~/Applications/MacClipboard-Dev.app` carries the change.
- Not done: the interactive pass. Everything the parse decides is covered by tests, but how the swatch actually looks in the popover, in both appearances, is a check by eye that has not been made; the checklist for it is in `CLAUDE.md` under "When modifying the colour swatch". No release build, no version bump.

### 2026-08-10 - Fast typing lost letters out of the search, and 0-9 were a mode nobody asked for

- Source: direct report. "If I type really fast it misses some letters, for example searching for pickup writes pckup", together with a request to remove the numbered-item shortcuts because they get in the way of searching.
- Summary: `0`-`9` no longer jump the selection, every printable key including digits starts or extends a search, and no key that could be a search term is dropped on the way to the field. `ClipboardSearchTyping` is the whole decision as a pure value, so the rules are stated in tests rather than in the middle of a 40-case switch.
- **The dropped letter was a handoff, not a slow app.** `KeyEventView.performKeyEquivalent` receives every key in the window whoever holds first responder, and the old path set `@FocusState` (which flips on assignment) then wrote the first character 20 ms later. AppKit moves first responder a runloop pass or two after the assignment, so keys pressed in that gap were tested against a flag that had already flipped, fell through as somebody else's problem, and reached a field that was not listening yet. Exactly one character was lost, the one after the first, which is why "pickup" came out as "pckup" and never "pckp". The 20 ms write was the second half of it: anything the field did receive in the meantime was overwritten.
- **The fix is to read the fact rather than the intention.** `ClipboardSearchField` is an `NSTextField` of the app's own that reports when it actually holds the keyboard, and until it does, `handleKeyEvent` keeps claiming keys and appending them to the search itself. Nothing is deferred any more, so there is no delayed write left to clobber anything. `unfocusSearch()` moves both flags together for the same reason in the other direction: a key typed while the field is on its way out belongs to a new search.
- SwiftUI's `TextField` could not do it. It cannot say when it has really taken the keyboard, and an `NSTextField` selects its whole contents on becoming first responder, which is what forced the delayed write in the first place: text put there before focusing would have been replaced by the next keystroke. The replacement takes focus with the caret at the end instead, which is what let the whole handoff become synchronous.
- **A second way to lose a letter, found while reading the switch and fixed with it**: a `case` that matches on key code and then fails its inner ⌘ test exits the switch, so the `default` arm that starts a search was never reached and `f`, `d`, `z`, `e`, `h`, `v` and `n` typed over the list did nothing at all. "favorite" searched for "avorite". The typing check therefore runs before the switch rather than inside it. This was `FOLLOWUPS.md`'s "Decide whether the letter shortcuts should still swallow the key when they decline it", which asked first whether search-on-any-letter is the intended model; the report answered that, so the entry is removed rather than parked.
- **Removing `0`-`9` is what lets a digit be searched for.** They only ever moved the selection, never pasted, and `isPrintableCharacter` had to exclude every digit for them to work, so a clip found by a year or a house number could not be typed at. The number badge on the first ten rows went with them: it was the label on the shortcut, and it cost the ten newest images the thumbnail every other image row gets.
- Also changed, because it widened every window above: the list's `.id(...)` was keyed on the live search text, so each keystroke threw the entire scroll view away and rebuilt it. It is keyed on the debounced text now, and the debounce is 120 ms rather than 300 ms, which is enough to stop a burst of keys starting a filter task each given the filtering already runs off the main thread.
- Two ordering races closed while implementing it, neither observed but both reachable: `syncFirstResponder` reads its wish off the view (`desiredFocus`) rather than off a captured struct, so a block scheduled by an earlier update cannot take the keyboard away from a search that has started again; and the field reports what is true when the report runs rather than when it was scheduled, so one responder change overtaking another cannot put the keyboard back in a field the user has already left.
- Verification: `xcodebuild build` (Debug, BUILD SUCCEEDED) and `xcodebuild test` (TEST SUCCEEDED, 0 failures) with 15 new tests in `MacClipboardTests/SearchTypingTests.swift`. They cover a letter and a digit starting a search, each of the eight letters that used to be swallowed, "pickup" typed entirely inside the handoff window arriving whole, the field getting its own keys once it has the keyboard, backspace only while a search is being typed, ⌘ and ⌃ leaving the key to the shortcut table while ⇧ does not, the navigation keys never counting as typing, and a note being written not being a search.
- Finished with `./run.sh`, so the dev copy in `~/Applications/MacClipboard-Dev.app` carries the change.
- Not done: the interactive pass. The timing is what this task is about and a test cannot press a key, so the checklist added to `CLAUDE.md` under "When modifying search or the popover's key handling" has not been walked on the running build, and the new search field's appearance in the popover is unconfirmed by eye. Released as v0.1.27 on the same day at the maintainer's request, so that check is owed on the shipped build rather than before it.

### 2026-08-10 - A multi-line clip could not be split into separate items

- Source: Product task 10 from `BACKLOG.md`, the mirror of task 9.
- Summary: `Cmd+Shift+M`, and a second entry in the row's context menu, turn the selected multi-line text item into one new item per line. `ClipboardTextSplit` holds the whole decision as a pure value, `plan(for:)` → `Plan` → `items(from:sensitivity:timestamp:)`, so the line rules, the ordering, the masking and the titles are testable without a store. It reuses Copy Merged's model rather than inventing one, which is what the entry asked for: the source is untouched, every piece lands as an ordinary new item through `insertIntoHistory`, masking can only be gained, and nothing is trimmed.
- **The pieces are inserted last line first.** Every insert goes in at position 0, so a forward loop would leave the list reading bottom to top and the user pasting their column backwards. Inserting in reverse is what satisfies the entry's "newest-first in reading order". The timestamps descend by a millisecond a piece for the second half of the same problem: the array order decides what the popover shows now, the timestamps decide the order after a relaunch, and nothing else would keep the two in step. There is a test on each.
- The one deviation from the entry, made during the work: it said drop **empty** lines, and what is dropped is lines with no non-whitespace character. A run of tabs between two blocks is a blank line in every way that matters, and a clip of three spaces arrives as a row showing nothing that cannot be told from an empty one. The rule that actually protects a leading tab is the separate one, that surviving lines are never trimmed, and that is kept exactly: `"\tindented "` splits out with both its tab and its trailing space. Dropping and trimming are separate decisions and only the first one is made.
- **The plan comes from the cursor's item, not the right-clicked row**, which is the call that took the most thought because a context menu ordinarily acts on what was clicked. Two things decided it. A right click does not move the selection in this list, so acting on the clicked row would need the menu to select it first, which `.contextMenu` gives no hook for. And a per-row plan means scanning the text of every visible clip on every list rebuild, where a clip can be megabytes and a rebuild happens on every keystroke in the search field. They are the same idea in opposite directions, and they can never both apply: `splitPlan` stands down when two or more rows are ⌘-clicked, which is exactly when `mergePlan` exists. So the context menu always offers exactly one of the two, and the greyed one says what would enable it.
- **It does not write the pasteboard**, where `copyMerged` does. A split has no single result to copy and the point of it is to paste the pieces one at a time afterwards, so replacing what the user has copied to do that would be taking something away. Named Split rather than Copy Split for the same reason.
- The cap is a confirmation, not a refusal: above 100 pieces an alert names the count, and names the history limit as well when the split would reach it, because that is the part the user cannot see coming. Nothing is capped after they confirm. `trimHistoryToLimitPreservingFavorites` is the existing answer to a history with too much in it and it keeps the newest, which after a reverse insert is the first lines of the source. The plan is held in `pendingSplitPlan` while the alert is up, so the confirmation acts on what the user was shown rather than on whatever the selection has become.
- Sensitivity is asked per piece rather than once over the clip, which the entry's wording ("each piece re-run through `ClipboardSensitivityPolicy`") implies and which is the more useful behaviour anyway: a password on line 4 masks the item it becomes and leaves the nine ordinary lines around it readable. Or-ed with the source's own flag, so a masked clip cannot be split into visible ones.
- A repeated line produces one row, not two, because the merger dedupes by content. `ClipboardTextSplitOutcome` counts those separately and the status banner says how many moved, since 12 lines becoming 11 rows otherwise reads as dropped text.

It is display only. ### 2026-08-10 - A multi-selection could only be built with the mouse

- Source: direct request, made straight after task 9 shipped and for the obvious reason: Copy Merged is a keyboard action on a selection there was no keyboard way to build.

Tested by extending, splicing a new item onto the front of the list, and extending again.

### 2026-08-09 - Everything arrived as plain text, whatever it was copied from

- Source: Product task 8 from `BACKLOG.md`.
- Scope change, made during the work and approved rather than assumed: the entry said "skip HTML in v1", and that turned out to be the wrong call, which the entry's own problem statement had already hinted at by naming a browser first. Shipped with RTF only, the very next real copy tested against it stayed plain, and reading the pasteboard said exactly why: Chrome had written `public.html` at 12,993 bytes and `public.utf8-plain-text` at 674, and no `public.rtf` at all. Apps split cleanly down the middle. Word, Notes, Pages, Mail and TextEdit write RTF; Chrome, Slack, VS Code and everything else built on a web view write HTML and nothing else. Storing one flavour leaves half of what a person copies arriving flattened, and the browser half is the bigger one. HTML was added as a second flavour before the task was closed, which is why the entry below describes both. What that cost, against the "doubles the storage and the failure modes" reasoning: one more inline attribute, one more shape check, and a per-flavour cap. What it did not cost was a rule for which flavour a paste prefers, which was the thing that had looked expensive: `NSPasteboard.availableType(from:)` answers with the first type in the *receiving* app's preference order, so writing both means a rich text editor takes the RTF and a web view takes the HTML from the same pasteboard, and choosing at write time would be answering a question that is not the sender's.
- Summary: A text clip now stores the pasteboard's RTF and HTML beside its plain text and writes back every flavour it has, so a styled paragraph copied out of Word, Notes, Pages, Mail, TextEdit, a browser or Slack arrives styled instead of flattened. Two tests failed on exactly that, which is how it was found rather than shipped: the short-circuit now compares both flavours too and falls through to the ordinary replace when either differs, so re-copying a clip as plain text stops it pasting rich, re-copying it rich starts it again, and copying the same words out of a browser after an RTF app swaps which flavour is kept, in every case without adding a second row. For the same reason the flavours are the one thing the merger does *not* inherit from the item it replaces, unlike favorite, note and the sensitivity flags: those are decisions the user made about the clip, while formatting is a property of the copy itself, and inheriting it would paste styling the most recent copy did not have and leave the row's marker up after the user deliberately re-copied plain. RTF has a signature to check. HTML does not, since what an app writes is a fragment that may begin `<meta`, `<!DOCTYPE`, `<html>` or a bare `<span>`, so `looksLikeHTML` scans the first 4 KB for a `<` that starts a tag name, tolerating the zero bytes of UTF-16 and rejecting prose like `a < b`; both are byte scans rather than parses, because parsing would cost an `NSAttributedString` round trip on every copy and the bytes are handed back raw on paste anyway. That also means they are not reachable by the image eviction that storage pressure runs, which is the thing to weigh if the 1 MB cap is ever raised. Measured: a styled sentence came to 480 bytes of RTF, a four-line styled paragraph to 668, and a real Chrome copy of a short passage to 12,993 bytes of HTML, so HTML is the larger of the two by an order of magnitude and is the one to watch.

### 2026-08-05 - Store images compressed, and give them their own retention window

- Source: P1 from `BACKLOG.md` (the storage limit silently capping history), plus the question of whether images should be managed differently from text.
- Summary: Measured a real 1859-item store first: 1683 text clips came to 717 KB, while 176 images came to 1.2 GB. The cause was not retention at all. `saveClipboardItem` stored `image.tiffRepresentation`, and AppKit writes TIFF uncompressed (`compression=none`, `bps=9`), averaging 7 MB per screenshot. Re-encoding 13 sampled stored images as PNG took 120 MB to 3.0 MB, about 40x smaller, losslessly. File items deliberately follow the text window, because a file clip stores only its paths and so costs about a line of text. The broken storage-limit behaviour is gone: instead of halving the retention window once (which could never reach the limit, and just kept history at half the requested age every hour, for ever), `evictImagesUntilWithin(byteLimit:)` drops oldest non-favorite images until the store actually fits, and `getStorageSize` now stats the store directory rather than faulting every external image in to add up its length, which was moving over a gigabyte per hourly pass. Bulk deletes switched from `NSBatchDeleteRequest` to batched object deletion, because a batch delete runs straight against the store and never tells Core Data to remove the external image files: that store still held 8 orphaned files (49 MB) from rows deleted months earlier, so deleting images to reclaim space could reclaim nothing. Favorites stay exempt from every automatic path.
- Verification: `xcodebuild test`, 30 tests, TEST SUCCEEDED. New tests assert stored bytes carry the PNG signature and are smaller than the TIFF for the same pixels while still decoding, that PNG re-encoding is idempotent and rejects non-image bytes, and that image cleanup's predicate cannot reach text or file items. The 40x figure and the 717 KB / 1.2 GB split are measurements from the reporting machine's own store, not estimates.

### 2026-07-21 - Persist "most recently used at top" ordering across app restarts

- Source: Bug report (favorites ordered by latest used at top reverted to creation-date order after a Mac reboot; user expected reboot not to change ordering).
- Summary: The use-order was only ever kept in memory. `ClipboardMonitor.copyToClipboard` moves a pasted item to the front of the in-memory array, but nothing wrote that to disk, and `PersistenceManager.loadClipboardHistory` rebuilt the list sorted purely by `createdAt`, so every restart discarded the last-used order (not a regression, just first surfaced on reboot). Added an optional `lastUsedAt` Date attribute to `PersistedClipboardItem` (lightweight inferred migration, nil for legacy rows), seeded it with the creation time on save, added `PersistenceManager.markItemUsed(itemId:)` (sets `lastUsedAt = Date()` without touching `createdAt`/`updatedAt`, so "time ago" still reflects capture time), called it from `copyToClipboard` after the in-memory move, and changed the load sort to order by `lastUsedAt ?? createdAt` descending. Applies going forward; existing history has no historical use times so it falls back to `createdAt` until each item is next used.
- Verification: `make dev` (Debug build succeeded).
