### 2026-08-09 - The global hotkey was hardcoded, so a collision left the user with nothing to change

- Source: Product task 7 from `BACKLOG.md`.
- Summary: ⌘⇧V is now the default rather than the definition. `GlobalHotkeyShortcut` (a new `GlobalHotkey.swift`, which is also where the old hardcoded enum moved out of `BuildInfo.swift` to) holds the pair Carbon actually takes: a virtual key code, which is a position on the keyboard rather than a character, and a modifier mask. It is stored as those two integers, `MenuBarController` unregisters and re-registers on every change, and `GlobalHotkeyRecorder` in Settings records a new one. The piece that needed finding rather than writing is that the recorder has to *let go* of the hotkey while it listens: a Carbon hotkey is taken system wide before the key event reaches the app, so the combination currently registered is the one combination a recorder could never capture, and pressing it would open the popover instead of being written down. `setGlobalHotkeyRecording(_:)` is that seam, and every exit from recording calls it back, including Escape, Cancel, the settings window losing key, and the hotkey toggle being switched off underneath a recorder whose own Cancel button it disables; a stranded monitor would swallow the next key press anywhere in the app. The recorder is a local `NSEvent` monitor rather than a first responder view, because the combinations worth recording are exactly the ones that are already key equivalents somewhere, and a local monitor runs before `performKeyEquivalent`, so ⌘⇧V gets recorded instead of performed and the settings window's own Done button does not fire on a recorded Return. Two combinations are refused, and both refusals are about other apps rather than about MacClipboard: no ⌘/⌃/⌥ at all would fire the hotkey while the user types, and ⌘ plus one key is how apps spell their menu items, so taking one globally removes Paste or Quit from everything they run. Function keys are the exception to the first rule, since F13 alone is a legitimate hotkey. The same validation runs on the value read back from disk, so a combination this build would refuse to record cannot arrive from an older one, and the four modifier bits Carbon takes are masked out of `NSEvent.modifierFlags` on the way in, so caps lock being down does not make two identical shortcuts compare unequal. Labels come from the current keyboard layout through `UCKeyTranslate` rather than a table of key codes to letters: key code 6 is Z on a US keyboard and W on a French one, and naming the wrong key would describe a keyboard the user is not looking at. `resetToDefaults()` does reset this one, unlike the three preferences it deliberately leaves alone, because a shortcut nobody can remember is exactly what Reset is for, and the default is also named on a button beside the recorder.
- Scoping calls: the entry's own, kept, was the global hotkey only. The in-popover keys stay behind one `shortcutsEnabled` switch, because rebinding them multiplies the conflict surface across the editor, the digit shortcuts, the arrow navigation and the reveal key for a fraction of the benefit. The dev and release split needed no new rule: the two builds have different bundle identifiers and therefore different preference domains, so each stores its own shortcut and `defaultForCurrentBuild` keeps the defaults apart, which is what the entry asked for when it said the two copies must still not fight over one combination.
- Not delivered as specified, and this is the honest half: the entry asked for the failure from `RegisterEventHotKey` to be surfaced as "that shortcut is already taken by another app" rather than a silently dead key. The surfacing is there and now names the combination and points at the recorder, in the popover banner and in Settings, but the signal underneath it is weaker than the entry assumed. Measured on macOS 26.5 with a throwaway helper process holding ⌃⌥N: a second process asking for the same combination got `OSStatus` 0, not `eventHotKeyExistsErr`. So the banner fires only for a registration macOS actually refuses, and the everyday collision still presents as a key that does nothing. This predates the recorder rather than being caused by it, and the recorder is the remedy either way, since a user who notices a dead key can now change it. Tracked in `FOLLOWUPS.md` with what was measured and why no public API answers it.
- Verification: `xcodebuild build` (Debug, BUILD SUCCEEDED) and `xcodebuild test` (94 tests, 0 failures, TEST SUCCEEDED, up from 79). Fifteen new tests. Ten over the value type: the per-build default, modifiers rendered in the order macOS uses them (asserted on the left arrow, whose label comes from a table rather than the keyboard layout, so the test does not depend on which layout it runs on), the named keys, both refusals, function keys standing alone, and the unsupported modifier bits being dropped. One asserts an invariant rather than a case: every key code from 0 to 200 produces a non-empty label with no control characters in it, because a shortcut the user cannot see is worse than an ugly one. Five cover the stored half over a `UserDefaults` suite of the test's own: a recorded shortcut survives a relaunch, nothing stored means the build's default, a stored ⌘V falls back to the default rather than taking Paste from every app, garbage values fall back, and Reset restores the default.
- Verified end to end on the running dev build, from outside the app, because the tests exercise the model and prove nothing about the registration: with ⌃⌥N seeded into the dev preference domain and the app relaunched, a synthesised ⌃⌥N key press put a 546x616 MacClipboard Dev window on screen, read back from `CGWindowListCopyWindowInfo`. With the preference then removed, the dev default ⌘⇧⌥V opened and closed the popover and ⌃⌥N did nothing, which is the pair that shows registration follows the stored value rather than a build-time constant. The same run is what produced the collision finding above.
- Not done: the recorder's own interaction was not driven programmatically, so clicking it, seeing a refusal message, and Escape or a lost key window ending the recording are checklist items in `docs/DEVELOPMENT.md` rather than verified here.

### 2026-08-09 - The DMG was notarized and stapled but never code signed

- Source: Priority task 2 from `BACKLOG.md`.
- Summary: `build.sh` handed the disk image from `create-dmg` straight to `notarytool` and `stapler`, so every release up to 0.1.22 shipped a container carrying a valid notarization ticket and no signature of its own. It now signs the image with the same Developer ID as the app, with a secure timestamp, before submitting it, and asserts the result the way Gatekeeper does. The ordering is the part that needed finding rather than writing: `codesign` rewrites the image, so signing one that has already been stapled drops the ticket, and it does so silently, with nothing to say so until `stapler validate` is run again. That was measured on a copy of the shipped 0.1.22 DMG, which validated as stapled, then reported "does not have a ticket stapled to it" the moment it was signed. So the three steps run in one order only, sign then notarize then staple, and the comment in `build.sh` says why rather than only what. `--identifier "com.macclipboard.installer"` is passed because codesign otherwise takes the signing identifier from the output file name: nothing pins the container's identifier the way the app's designated requirement is pinned, but renaming the DMG should not quietly change what was signed. The guard is `spctl -a -t open --context context:primary-signature`, run on the finished image and fatal to the build, chosen because it is the one check that needs the signature and the ticket to both be there, so it fails if either half regresses. It is gated on notarization having run, since without a ticket the honest answer is `Unnotarized Developer ID` and failing the build there would only punish a deliberate `SKIP_NOTARIZATION` build. The pre-flight in `docs/RELEASE_SMOKE_TEST.md` gained three checks, `DISTRIBUTION.md` documents the second assessment, and `CLAUDE.md` records the ordering rule next to the entitlements rule it rhymes with.
- Scale note, unchanged from the entry: this was a gap against Apple's guidance, not a broken download. The app inside was always correct, and it is the app that users run.
- Verification: end to end, on a scratchpad copy of the shipped 0.1.22 DMG rather than a new release build, so nothing in `build/` was touched and no tag or GitHub release was created. Baseline first, reproducing the entry exactly: `stapler validate` said the validate action worked, `codesign -dvvv` said "code object is not signed at all", and the assessment was `rejected, source=no usable signature`. Then the exact commands the script now runs. After signing: `codesign -dvvv` names the Developer ID Application authority, the Developer ID and Apple Root CAs, `TeamIdentifier=K542B2Z65M` and a `Timestamp`, `codesign --verify` reports valid on disk and satisfying its designated requirement, and the assessment moves to `rejected, source=Unnotarized Developer ID`, which is the right answer for a signed image with no ticket. After `notarytool submit --wait` (status: Accepted, submission c9ad8509) and `stapler staple`: the staple and validate action worked, `codesign --verify` still reports valid on disk, so stapling does not disturb the signature it was applied over, and the guard the build now runs answers `accepted`, `source=Notarized Developer ID`, with `origin` naming the project's Developer ID Application certificate, exit code 0. `hdiutil verify` reports the checksum VALID, so signing left a mountable image rather than a corrupt one. `bash -n build.sh` passes.
- Not done: no release was cut, so the change is proven on the commands rather than on a run of `./build.sh` itself. The next release exercises the real path, and fails loudly if the assessment is rejected.

### 2026-08-09 - Turning saving off left the whole history on disk, and nothing could clear it on quit

- Source: Product task 6 from `BACKLOG.md`.
- Summary: Two halves of one promise. `persistenceEnabled` only guards `saveItemToPersistence` and `loadPersistedHistory`, so switching "Save clipboard history" off stopped the writes and the load and deleted nothing: every clip from before that moment stayed on disk, invisible in the popover, which is the opposite of what the toggle reads as. Settings now offers to delete it at the moment the toggle goes off, and the offer is specific rather than reassuring. `PersistenceManager.savedHistorySummary()` counts the clearable rows and the favorites separately with `count(for:)`, which costs nothing on a store of images, and reads the store size, so the confirmation names how many items it would take, how many favorites it would keep, and what the history uses today. The size is deliberately phrased as what the history uses and never as what deleting frees: SQLite keeps its allocated pages, and only the external image files come back at once. Nothing is asked when `clearableCount` is zero, so a store holding only favorites, or none at all, produces no dialog. It stays an offer rather than an automatic delete because someone may be switching saving off for an afternoon and want their history back afterwards, and declining says so, with a line naming the count that was kept. The second half is `clearHistoryOnQuit`, the answer to "keep history while I work, keep nothing afterwards". `ClipboardMonitor.clearHistoryOnQuitIfRequested` runs `clearAllData()` on the caller's thread rather than going through `clearHistory()`, which hops to a utility queue: the process is exiting, so a dispatched delete would be abandoned halfway and the preference would quietly do nothing. `performOnContext` is `performAndWait`, so the rows and the image files are gone before it returns. `AppDelegate.applicationWillTerminate` is the only caller, through a passthrough on `MenuBarController` that is deliberately *not* part of `cleanup()`, which `deinit` also calls: a controller being deallocated is not a quit, and clearing a user's history from a deallocation would be the worst kind of surprise. SIGTERM is covered by the same call site, because `installTerminationSignalHandler` turns it into `NSApp.terminate`, so a logout and the Homebrew cask's TERM both clear. Both paths go through `clearAllData`, so favorites are spared by the one `AND` in `bulkDeleteNonFavorites` rather than by a second rule that could drift. `resetToDefaults()` leaves `clearHistoryOnQuit` alone, joining `excludedBundleIdentifiers` and `capturePaused` for the same reason each of those is exempt: turning it off there would leave a history the user expected gone sitting on disk after the next quit, with nothing on screen saying so.
- Scoping calls: the quit toggle is not disabled while saving is off, because a store the user declined to purge is exactly the case where it still has work to do. The toggle's help text states the limit rather than implying a guarantee it cannot make, which is that a force quit or a power cut leaves the history on disk since nothing gets to run at that point. No vacuum of the SQLite file: the images are the storage cost and object deletion already removes them, while the file itself holds text, which a measured history put at under a megabyte for 1683 clips.
- Verification: `xcodebuild build` (Debug, BUILD SUCCEEDED) and `xcodebuild test` (TEST SUCCEEDED), with seven new cases. Four cover the quit clear over a real Core Data stack: with the preference on, quitting leaves the favorite and takes the text and the image, in memory and on disk together, asserted with no wait at all, which is the property that matters since at quit there is no later and a dispatched clear would leave every row in place; with it off, quitting deletes nothing; with saving already off, the clear still runs, because that is the store the offer was declined on; and `resetToDefaults()` leaves the preference on while still restoring `persistenceEnabled`. Three cover the numbers the confirmation puts in front of a user, since a count wrong in either direction is worse than no count: a mixed store separates the three clearable items from the two favorites and reports a non-zero size, an empty store offers nothing, and a store of only favorites offers nothing while still counting the favorite.
- Verified end to end on the running dev build, because the tests call the method directly and so prove nothing about the terminate wiring, which is where this feature can silently do nothing. Over a real dev store of 348 items, 48 of them images, with three rows marked favorite and the store backed up first and restored afterwards. With the preference off, `kill -TERM` left all 348 rows: the SIGTERM handler ran and the clear correctly declined. With it on, the same `kill -TERM` left exactly 3 rows, the 3 favorites, took the external image files from 35 to 5 and the store from 14.9 MB to 1.5 MB, and logged `💾 Clearing saved history on quit, as requested in Settings` 0.8 ms after `[App] Received SIGTERM, shutting down cleanly`, with the process gone immediately after. That sequence is what shows the whole delete, rows and external files, completed inside `applicationWillTerminate` rather than being abandoned with the process.
- Observation, not a regression: the cleared store kept 5 external image files for 2 favorite images. Consistent with the orphans described in priority task 3, which remains open.

### 2026-08-09 - A test could not touch persistence without touching the user's clipboard history

- Source: Priority task 1 from `BACKLOG.md`.
- Summary: `PersistenceManager` now takes a `StoreLocation`, and only `shared` holds the `.applicationSupport` case; anything else names its own directory, which is what tests use. That is the seam the entry asked for, but the more interesting half of the work was what looking for the hazard turned up. `xcodebuild test` launches MacClipboard itself as the test host, so `applicationDidFinishLaunching` ran on every test pass, and 0.25 seconds in it built `MenuBarController(clipboardMonitor: ClipboardMonitor())` unconditionally. Nobody had to write a bad test for the store to be opened: every run already loaded the dev history, polled the pasteboard for the length of the run, ran the hourly maintenance timer against it and could start the one-time image re-encode. So the fix is in two parts. `PersistenceManager.shared` traps under a test host, because `ClipboardMonitor.init` defaults to it and a forgotten injection would otherwise be silent, with the damage landing in the user's history rather than in a red test; and `applicationDidFinishLaunching` now skips the menu bar and the monitor for a test host, alongside the instance takeover and the installation alerts that were already guarded. The test-host check moved to `BuildInfo.isHostingTests`, since three files need it now. `UserPreferencesManager` gained an injectable `UserDefaults` for the same reason: the preferences decide whether persistence runs at all, so a machine with it switched off would have failed an unrelated test, and `imageStorageCompacted` is written during ordinary use, so a test on the standard domain would change what the developer's own copy did at its next launch.
- Deviation from the entry, deliberate: the tests use an on-disk store in a temporary directory rather than the in-memory store the entry named. `NSInMemoryStoreType` has no external binary storage and no files, so `getStorageSize()` reads zero and `evictImagesUntilWithin` returns immediately, which would have left the storage-pressure case, one of the four the entry asked for, untestable. A temporary SQLite store exercises the same code as production, including the external image files that batched object deletion exists to remove, and it satisfies the requirement that mattered: nothing can reach the real store.
- Verification: `xcodebuild build` (Debug, BUILD SUCCEEDED) and `xcodebuild test` (72 tests, 0 failures, TEST SUCCEEDED, up from 62). Ten new tests. Five over the favorite guarantee, one per automatic path: age cleanup, image-scoped cleanup (which also asserts it cannot reach a text item), `clearAllData`, storage-pressure eviction, and that `deleteItems(withIds:)` does remove a favorite that was named directly. Two drive a real `ClipboardMonitor` over a store of its own: re-copying a favorite records `save(original), save(newer), save(replacement), delete(original)` in that order, through a recording subclass, so the save-before-delete ordering that 0.1.x lost items to is pinned rather than described, and clearing history leaves the favorite in memory and on disk together. Three cover the seam itself, including that a test run is still recognised as one, which is the premise the trap rests on. The trap was verified by running a throwaway test that touched `PersistenceManager.shared`: the host died with `EXC_BREAKPOINT` and logged `PersistenceManager.swift:20: Precondition failed: PersistenceManager.shared opens the store holding the user's clipboard history...`, and the test was then removed. That the hazard is really gone was checked from outside the code as well: the dev store's files were last written at 19:37, before the test runs at 20:17 to 20:26, and the host logs `[App] Hosting an XCTest bundle; not starting the menu bar or the clipboard monitor`. Finished with `./run.sh`; the installed dev copy came up `trusted=true` with `duplicates=[]`.
- Not done: a Release-configuration build was deliberately not run, because `CLAUDE.md` documents that a bare `xcodebuild -configuration Release build` ad hoc signs the release bundle id into shared DerivedData and gets it registered as a duplicate install. The release store path is unchanged by construction: `usesContainerDefaultLocation` is true only for `.applicationSupport` on a non-dev build, and in that case `configure` leaves the container's own description exactly as it was.

### 2026-08-09 - Capture could only be stopped by quitting the app

- Source: Product task 4 from `BACKLOG.md`.
- Summary: Added a user-controlled pause. `ClipboardMonitor.setCapturePaused` is the single writer of a new `capturePaused` preference: it stops the polling timer, drops anything the deferred-capture path was still holding, and publishes `isCapturePaused` for the UI. `checkClipboard` guards on it too, because the timer is not the only caller: `refreshClipboardNow` runs on every popover open, and `startMonitoring` does an immediate check. The rule with teeth is on the way back, and it is the one the backlog entry was written around: resuming adopts the pasteboard's current change count *before* the timer restarts (`ClipboardCapturePause.changeCountOnResume`), because `changeCount` still holds the last clip that was captured and the first tick would otherwise record the very clip the user paused in order not to record, 0.8 seconds after they resumed. `startMonitoring` was made idempotent, since resuming and the initial history load can both reach it and two timers would poll for ever. The state is stored, so a pause survives a relaunch and a paused app comes back paused rather than quietly recording again at the next login. It is visible from outside the popover: the menu bar icon becomes a clipboard with a line struck through it, composed in `MenuBarController.slashed(_:)` because SF Symbols ships no slashed clipboard in any weight, and swapping to a generic `pause` glyph would have cost the user the one thing that icon is for, which is knowing at a glance which icon is MacClipboard; the controller observes `$isCapturePaused` so the icon cannot lag behind the state, and the tooltip and accessibility label say "capture paused" because the glyph alone cannot. Three controls flip it: a Pause Capture / Resume Capture item in the right-click menu (titled by what it does, rather than a checkmark that has to be read twice), a pause button in the popover header, and a Resume button on a new popover banner. With no history at all the empty state says "Capture is paused" and offers to resume, instead of telling the user to copy something, which would do nothing. `resetToDefaults()` deliberately leaves `capturePaused` alone, on the same reasoning as `excludedBundleIdentifiers`: someone who paused before a screen share and then opened Settings should not come out of it recording, and lifting the pause is one click on an icon that is showing it the whole time.
- Scope note: no keyboard shortcut. The entry did not ask for one, and every free combination in the popover costs something against the editor and the digit shortcuts, which `CLAUDE.md` documents as finely balanced. The menu bar item is reachable without the popover, which is where the need actually arises.
- Verification: `xcodebuild build` (Debug, BUILD SUCCEEDED) and `xcodebuild test` (62 tests, 0 failures, TEST SUCCEEDED), including three new cases pinning the resume rule: a clip copied while paused is not new after resuming, the next copy after that is, and a pause with nothing copied in between loses nothing. The composed icon was rendered off-screen at 8x from the same drawing code and checked to read as a struck-through clipboard rather than a smudge at menu bar size.

### 2026-08-09 - Nothing could be excluded from capture, and concealed clips were still written to disk

- Source: Product task 5 from `BACKLOG.md`.
- Summary: Added a capture guard that is separate from the existing display rule. `ClipboardCapturePolicy` (in `ClipboardMonitor.swift`, beside `ClipboardSensitivityPolicy`) decides whether a pasteboard change is recorded at all, and returns `.capture`, `.skipConcealed`, or `.skipExcludedApp`. It runs in `checkClipboard` before the pasteboard is read, after `changeCount` has already moved, so a skip is final rather than reconsidered on the next tick, and a skipped clip is never queued for the deferred-capture retry: the point of it is to leave no trace, and queueing would have burned twenty retries reaching the same answer. Two preferences drive it. `skipConcealedClips` honours `org.nspasteboard.ConcealedType` and `TransientType`, the marker password managers set to say "do not record this", so it has no false positives. `excludedBundleIdentifiers` is a list of apps, with an `NSOpenPanel` picker in Settings > Privacy and a row per app showing its icon and name; the preference stores identifiers only, and `ExcludedAppRow` resolves names and icons at display time so an app the user has since uninstalled still reads as excluded, marked "not installed", instead of dropping off the list. `attemptPendingCapture` re-checks the concealed type on each retry, because an app that writes its clip in stages (which is why that path exists) can declare the type after the change count moved, but deliberately does not re-read the frontmost app: by then the user may have switched, which answers a different question, so the app verdict is made once when the change is noticed. The known limit is stated in the Settings copy rather than papered over: with 0.8 s polling the frontmost app is a good guess at the source of a clip and not a fact, while the concealed-type rule is exact because the source app marks the clip itself. `resetToDefaults()` deliberately leaves `excludedBundleIdentifiers` alone; every other preference is recoverable by setting it again, but emptying that list silently resumes recording from a bank or a terminal, and the entries are removable individually in front of the user.
- Deviation from the backlog entry, at the requester's instruction: `skipConcealedClips` ships **off** by default, not on. The entry argued for on, on the grounds that honouring the source app's own marker is not a heuristic. Off keeps a default install capturing exactly what it captured before, and makes dropping a clip an explicit choice, which is defensible because a skip loses the clip rather than hiding it. The consequence is the one the entry was written about: on a default install a password copied out of a password manager is still stored in plain text unless the user turns this on. The Settings copy states both halves, and flipping the default is tracked in `FOLLOWUPS.md`.
- Verification: `xcodebuild build` (Debug, BUILD SUCCEEDED) and `xcodebuild test` (40 tests, 0 failures, TEST SUCCEEDED), including eight new cases in `SensitiveContentDetectorTests` over the guard: a concealed clip is skipped only when the preference is on, an ordinary clip is captured with the guard on, an excluded app is skipped while other apps are not, matching is on the whole bundle identifier (so `com.example.bank.helper` and `com.example` are not caught by `com.example.bank`), a source with no bundle identifier is captured rather than matched by accident, the concealed marker is reported ahead of the app guess when both apply, and both guards off (the default install) skips nothing. One case covers the pairing with the display rule: a concealed clip captured with the guard off is still only masked when `autoDetectSensitiveData` asks for it.

### 2026-08-07 - Building from Xcode took the dev build's Accessibility grant away

- Source: Report from a dev build showing "Accessibility permission stopped working" during ordinary work on the editor feature, with the release copy unaffected.
- Summary: The Debug configuration built with `PRODUCT_BUNDLE_IDENTIFIER = com.macclipboard.app.dev`, the same id `run.sh` gives the signed copy in `~/Applications`, and Xcode signs its own products ad hoc (`CODE_SIGN_STYLE = Automatic` with no team). So every Run and every `xcodebuild test` put a differently signed binary behind the id that holds the grant, and tccd logged `Failed to match existing code requirement for subject com.macclipboard.app.dev and service kTCCServiceAccessibility` while `AUTHREQ_RESULT` came back `authValue=0` for the properly signed copy, which had `accessibilityWasGrantedV1` set and so reported `.staleRecord`. The diagnosis was right and the cause was local: it is the duplicate-copy problem documented for the release id, reproduced inside the dev id. The Debug configuration now builds `com.macclipboard.app.debug` with display name "MacClipboard Debug", and `run.sh` alone promotes a copy to `.dev` after re-signing it with the persistent dev certificate, so an Xcode Run or a test host can no longer touch the dev grant and gets its own `UserDefaults` domain as well. Three related fixes came with it. `run.sh` now passes `--entitlements` on its re-sign and fails if the apple-events entitlement is missing afterwards: `codesign --force` replaces a signature wholesale, so the dev build had been running with no entitlements at all while the release had `com.apple.security.automation.apple-events`, which is the same defect `build.sh` fixed for release in 0.1.13. `handleAccessibilityPermissions` no longer fires the one-shot system prompt for a test host or an ad hoc signed dev build, since such a grant is pinned to a binary hash the next build changes, and the banner names that case from `PermissionManager.cannotHoldGrant` instead of sending the developer to System Settings; the `.staleRecord` text also drops "usually after an update" for dev builds, where no update ever happens, and points at `./run.sh --reset-permissions`. That flag now also clears `hasRequestedAccessibilityPromptV1` and `accessibilityWasGrantedV1`, and runs *after* the old process has exited: it used to run first, and cfprefsd wrote the live process's cached values back on quit, so the reset silently put both keys straight back and the next launch had no record, no way to ask for one, and a banner still claiming permission had stopped working.
- Verification: `xcodebuild build` (Debug, BUILD SUCCEEDED) and `xcodebuild test` (TEST SUCCEEDED); `bash -n run.sh scripts/clean-dev-artifacts.sh`; the Debug product's `CFBundleIdentifier` reads `com.macclipboard.app.debug` and the installed dev copy still reads `com.macclipboard.app.dev` with `designated => identifier "com.macclipboard.app.dev" and certificate leaf = H"b6d2…"` and `com.apple.security.automation.apple-events` present. After `./run.sh --reset-permissions`, `defaults read com.macclipboard.app.dev` keeps `accessibilityWasGrantedV1` deleted (it came back on the run before the ordering fix), so the banner reports "permission required" rather than "stopped working", and tccd logs no further requirement mismatch for the `.dev` subject while the test hosts query under `.debug`.

### 2026-08-05 - Upgrading broke Accessibility for every user, and the 0.1.16 migration could crash on launch

- Source: Bug report ("still permission issue after upgrade", after `brew upgrade --cask macclipboard` 0.1.15 to 0.1.16). The reporter's concern was other users hitting the same thing, which they do: both faults below are on the upgrade path, not specific to a development machine.
- Summary: Two separate defects, found from the reporting machine's own unified log. **First, the upgrade breaks Accessibility for the instance that is running.** The log is unambiguous: PID 57425 launched from `/Applications` at 19:46 as 0.1.15 with `trusted=true duplicates=[]`, and at 22:49, with no user action but the upgrade in between, the same PID reported Accessibility denied; a fresh process from the same path then logged `trusted=true` immediately, with no TCC change at all. `brew upgrade --cask` moves the old bundle aside and moves the new one into the same path without quitting the app, and macOS stops honouring the running process because the code identity it recorded no longer matches the binary now at its path. Pinning the designated requirement (which the release does) does not help: it keeps the grant valid for the *new* copy, not for a process whose bundle has been swapped. Homebrew is supposed to quit the app first and did not, and cannot be relied on to: `Cask::Artifact::AbstractUninstall` decides whether the app is running via a JXA `Application(id).running()` call, which needs Automation consent for the calling terminal, and via `launchctl list` labels, and neither reports a menu bar app started as a login item, so it silently skipped both the cask's `signal:` directive and its own upgrade-quit. The user's upgrade output shows no `Quitting application` and no `Signalling 'TERM'` line. Worse, the cask's `postflight` then ran `open -a`, which with the old process still alive just activates that process, so the user is left on the copy macOS refuses, and the banner blamed a stale TCC record and offered Repair, i.e. `tccutil reset` of a grant that was working. Fixed on both sides. In the app: `AppInstallation.BinaryFingerprint` records the running executable's inode and code directory hash at launch, `wasReplacedInPlace()` reports when a *different* build has taken our path (inode change alone is not enough, so re-copying an identical build does not trigger it, and an unreadable signature mid-upgrade reads as "not yet"), a 5 second poll in `AppDelegate` watches for it, and `relaunchAfterInPlaceUpdate()` starts the new copy and quits this one only once the replacement is actually up, so a bundle that cannot launch leaves the user with a working app rather than nothing. This works for every install method, including a drag from the DMG. `PermissionManager.Diagnosis` gained `.updatedInPlace`, checked before every other case, so the banner says "MacClipboard was updated and needs to restart" with a Restart button instead of offering to delete a good grant. The cause: `loadClipboardHistory` and `loadImageData(for:)` both returned `PersistedClipboardItem` objects out of `performOnContext` and then read their properties on the caller's thread. The one-time 0.1.16 image re-encoding made that reliably fatal, because it calls `refreshAllObjects()` between batches, dropping the snapshot behind a row the UI is still reading, and it runs exactly once per install: on the first launch after upgrading. Both now convert to `ClipboardItem` (a struct) or read the bytes inside the block, `performOnContext` documents the invariant, and the shared scheme passes `-com.apple.CoreData.ConcurrencyDebug 1` so any future off-queue access traps where it happens instead of corrupting the graph and crashing elsewhere. Also cleaned up the noise that made this report harder to read: `build.sh` now archives into `build/DerivedDataRelease` and removes it afterwards, so a release build no longer leaves a bundle carrying the release id in the shared DerivedData for LaunchServices to register as a duplicate install, and it finishes by running `clean-dev-artifacts.sh` in report mode. That script no longer calls a dev-id build product under the repo's own `build/` a stray.

### 2026-08-05 - Store images compressed, and give them their own retention window

- Source: P1 from `BACKLOG.md` (the storage limit silently capping history), plus the question of whether images should be managed differently from text.
- Summary: Measured a real 1859-item store first: 1683 text clips came to 717 KB, while 176 images came to 1.2 GB. The cause was not retention at all. `saveClipboardItem` stored `image.tiffRepresentation`, and AppKit writes TIFF uncompressed (`compression=none`, `bps=9`), averaging 7 MB per screenshot. Re-encoding 13 sampled stored images as PNG took 120 MB to 3.0 MB, about 40x smaller, losslessly. So: images are now stored as PNG (`NSImage.clipboardStorageData`, falling back to TIFF if re-encoding fails, since keeping the image beats keeping it small), and `compactImageStorage` re-encodes an existing history once per install, in batches of five with a refresh between so peak memory stays a few images, guarded by `imageStorageCompacted` and only replacing a blob when the PNG decodes and is smaller. Retention is now split: `persistenceDays` for everything and a new, shorter `imagePersistenceDays` (default 30) for images alone, via `cleanupOldItems(olderThan:scope:)`. File items deliberately follow the text window, because a file clip stores only its paths and so costs about a line of text. The broken storage-limit behaviour is gone: instead of halving the retention window once (which could never reach the limit, and just kept history at half the requested age every hour, for ever), `evictImagesUntilWithin(byteLimit:)` drops oldest non-favorite images until the store actually fits, and `getStorageSize` now stats the store directory rather than faulting every external image in to add up its length, which was moving over a gigabyte per hourly pass. Bulk deletes switched from `NSBatchDeleteRequest` to batched object deletion, because a batch delete runs straight against the store and never tells Core Data to remove the external image files: that store still held 8 orphaned files (49 MB) from rows deleted months earlier, so deleting images to reclaim space could reclaim nothing. Favorites stay exempt from every automatic path.
- Verification: `xcodebuild test`, 30 tests, TEST SUCCEEDED. New tests assert stored bytes carry the PNG signature and are smaller than the TIFF for the same pixels while still decoding, that PNG re-encoding is idempotent and rejects non-image bytes, and that image cleanup's predicate cannot reach text or file items. The 40x figure and the 717 KB / 1.2 GB split are measurements from the reporting machine's own store, not estimates.

### 2026-07-21 - Persist "most recently used at top" ordering across app restarts

- Source: Bug report (favorites ordered by latest used at top reverted to creation-date order after a Mac reboot; user expected reboot not to change ordering).
- Summary: The use-order was only ever kept in memory. `ClipboardMonitor.copyToClipboard` moves a pasted item to the front of the in-memory array, but nothing wrote that to disk, and `PersistenceManager.loadClipboardHistory` rebuilt the list sorted purely by `createdAt`, so every restart discarded the last-used order (not a regression, just first surfaced on reboot). Applies going forward; existing history has no historical use times so it falls back to `createdAt` until each item is next used.
- Verification: `make dev` (Debug build succeeded).
